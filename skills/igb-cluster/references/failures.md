# Failure modes on the IGB biocluster

Each row cost a session to find. The order is roughly the order a naive run hits them.

| # | Symptom | Layer | Diagnosis -> fix |
|---|---|---|---|
| 1 | Need a sequence, sandbox has no network | local | Resolve on the cluster from `$BIODB/pdb_seqres_2022_09_28.fasta`. Never type a sequence from memory |
| 2 | Job run locally, takes forever / no GPU | local | The laptop GPU is not reachable from the sandbox. CUDA work goes to the cluster |
| 3 | Job PENDING for a day | partition | Submitted to `gpu`. Use `admin` (idle A6000) unless the A6000 is unsuitable |
| 4 | **PENDING forever, `Reason=Resources`, no error** | resources | `--mem` over the node ceiling (60 GB on `admin`). `scontrol show job <id> \| grep -E 'Reason\|TRES'`. **The only silent failure here** |
| 5 | Job dies early in a temp-file step | node | Unguarded `mkdir /scratch/$SLURM_JOB_ID`; nodes report `TmpDisk=0`. Guard it, fall back to `$PWD/tmp` |
| 5b | **`submit_job` fails with `ssh: connect to host biologin.igb.illinois.edu port 22: Connection timed out`, while `call_command` works fine** | transport | Recurring; seen 2026-10-06 and twice on 2026-10-13, at a different stage each time. **The hostname is a red herring — do not chase it and do not file a ticket about the alias.** Measured on the login node 2026-10-13: `biologin.igb.illinois.edu` → **72.36.81.41**; `hostname -I` on biologin-3 → **72.36.81.41**; reverse DNS on 72.36.81.41 → **biologin-3.igb.illinois.edu**. One machine, two names, single public address — the working and the failing connections go to the same IP and port. `biologin-1`/`biologin-2` no longer resolve, so the round-robin has one member. There is no other host to point at, and no hostname setting is exposed (`provider_params` raises `NotSupported` on ssh targets). Treat it as a flake on a route that demonstrably works — and **check whether the job ran**, see 5c |
| 5c | `submit_job` reported a transport failure, so you assume nothing ran | transport | **Verified twice on 2026-10-13: the Slurm job had dispatched and was RUNNING.** Only the client-side `_submitted` marker write failed, which leaves the job untracked — `ledger()` stays empty, no `compute_done` ever arrives, and the client-side `run_timeout_s` never fires, so a runaway job runs until it finishes or you cancel it. **Always** `squeue -u $USER` and `sacct -u $USER -S <date> -X` after a failed submit; the uuid prefix in the error text matches the Slurm job name `operon-<first 8 chars>`. Harvest by hand from `<scratch>/.claude-science/jobs/<uuid>/`, and `scancel` it if you no longer want it |
| 5d | **A job script written on Windows fails with `ambiguous redirect`, or writes a file whose name ends in a carriage return** | script | CRLF line endings. `2>&1` becomes `1\r`, and `> out.log` creates `out.log\r`. Observed 2026-10-13: a `gtdbtk check_install` job "completed" with `exit=1` and an empty log, while the real 134-byte output sat in a file named `check_install.log\r`. The whole check never ran. **Write every job script with LF endings** (in Python, `open(path, "w", newline="\\n")`); when a job's output looks mysteriously empty, `ls -b` the workdir and look for `\r` in filenames |
| 5e | A read-only probe dies with `command timed out after 60s` | transport | There is a per-command timeout, but it is **not** a fixed 60 s — calls of 146 s and 200 s have completed normally on 2026-10-13, while a recursive `find` over `/private_stores/mirror` and a `du -sh` on a large tree both died at 60 s. Treat it as "slow filesystem walks get killed": prefer `ls -1d` at one level over `find`, avoid `du` on the mirrors, and put any genuinely long walk in a job |
| 5f | **A job shows `State=FAILED, ExitCode=124:0` with no error in its own log** | job | 124 is a `timeout` kill, not a tool failure. The generated `job.sh` wraps your command as `timeout <run_timeout_s + 300> bash -eo pipefail ./cmd.sh`, so a job that needs longer than the `run_timeout_s` you passed is killed mid-stride and its output just stops. Hit 2026-10-13: `gtdbtk check_install` was given 1200 s, died at 25:05 (= 1500 s + overhead) partway through validating the skani directory, having passed every earlier check. **Before blaming the tool, grep `job.sh` for `timeout` and compare with the elapsed time in `sacct`.** Reference-data validation over `/private_stores/mirror` is slow — budget hours, not minutes |
| 5g | `call_command` dies at 60 s, or at 600 s even though you asked for more | transport | The default is short and unreliable (one call died at "60s" while others ran 586 s and 656 s untouched), and **600 s is a hard ceiling** — `run_timeout_s=900` still failed with "timed out after 600s". Pass `run_timeout_s` explicitly on anything that might take more than a few seconds, keep it under 600, and put genuinely long work in a job. Do not `sleep` inside a `call_command` poll loop for more than ~9 minutes |
| 6 | `submit_job` raised, but a job is queued | transport | A dead connection can follow a successful `sbatch`. **Check `sacct` for `operon-*` before resubmitting.** The uuid is in the error text; the job is unrecoverable client-side (`ledger()` stays empty, `attach_job` raises NotFound) so harvest by hand with `c.download` from `<scratch>/.claude-science/jobs/<uuid>/` once `sacct` shows COMPLETED |
| 7 | `PermissionError` reading harvested outputs | local | `hpc/<job_id>/` is outside the sandbox: the python/bash kernels cannot read or list it, though `read_file` and `save_artifacts` can. `save_artifacts` first, then read back via `host.artifact_path(version_id)` |
| 8 | Job COMPLETED, no log to read | script | `slurm-<jobid>.out` is never harvested. `tee` into a named `run.log` and name it in `outputs` |
| 9 | Outputs missing after a successful job | script | Tool wrote to an absolute path. Only files under the job workdir are transferred back |
| 9b | A command after `module load` runs against the **system** python (3.6.8), or fails with `libpython3.10.so.1.0: cannot open shared object file` | shell | `module load` was **piped** (`\| head`, `\| tee`) or command-substituted, so it ran in a subshell and the load was discarded. `module list` will say "No modules loaded". Run `module load` bare on its own line |
| 10 | `sc.tl.leiden` raises on the scanpy module | env | Module has no leidenalg/igraph. `module load cs/scanpy-leiden` |
| 11 | matplotlib warns / fails on a read-only home | env | `export MPLCONFIGDIR="$PWD/.mplcache"` |
| 12 | Job workdir holds only `cmd.sh`, `job.sh`, `_staged` | transport | Normal. `ssh://` input symlinks are created at job **start**, not at submit. Not a staging failure; not a reason to resubmit |
| 13 | Client-side timeout stopped the job | transport | It did not. The Slurm job stays queued, runs, and completes, leaving outputs plus `_status.json` in `<scratch>/.claude-science/jobs/<uuid>/`. Wait for COMPLETED and `c.download`, do not resubmit |
| 14 | A job you submitted has vanished | user | The user cancels jobs under their own uid without saying so. Re-check `squeue`/`sacct` before reasoning about it |
